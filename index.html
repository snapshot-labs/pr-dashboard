How to read this graph

Read the graph left to right. A PR sits to the right of the things it needs. One card per PR; an arrow runs from a prerequisite rightward to the PR that waits on it. A deep graph is a wide one: it scrolls sideways rather than shrinking. Hovering a card or an arrow gives the full title and the edges it sits on.

  • Every arrow runs from a prerequisite rightward to the PR that waits on it, so the leftmost column merges first and the rightmost column merges last. A PR with no arrow arriving at it has nothing left to wait for.
  • Order is the horizontal axis only. One column is one rank, and the PRs stacked inside a column are independent of one another — none of them waits on any other, so they can merge in any order or all at the same time. How high or low a card sits in its column means nothing; it is just packing. Each column header says how many PRs stand under it and repeats that there is no order between them.
  • Every PR is drawn exactly once, as one card carrying its repo, its number and its title. A PR that two others need is one card with two arrows leaving it, not two cards.
  • Whole chains are drawn, not just tony8713's share of them. If one PR in a chain is tony8713's, or one of @chai3-bot's, every PR joined to it — following the arrows in either direction — is drawn too, whoever wrote it. A chain with none of theirs in it is not drawn at all, and nothing arrives here except through a declared dependency.
  • Every card that is not tony8713's says so, wherever it sits: dashed, and marked ◇ @handle, including one that starts a chain and has prerequisites of its own. An unmarked card is tony8713's — that marker is the only thing that says whose a PR is, so read it.
  • A tracked bot's PR is dotted, not dashed — @chai3-bot — and it is on this page for a different reason from every other card that is not tony8713's. A dashed card is here because it stands in the way of tony8713's work; a dotted one is here because it is work this page schedules, so it appears alone or mid-chain on its own account, takes arrows in and out, and is release-gated like any other. It still carries ◇ @handle, and it is not counted in tony8713's open-PR total at the top — it has its own count beside it.
  • The colour a card is filled with is the state of that PR — ○open, ◌draft, or ●merged. It says nothing about whether a PR is ready; that is what the arrows say. Every card also prints its state as a glyph and a word beside its ref, so none of it rests on telling one colour from another. A merged card is only ever a prerequisite that has already landed — this page lists open PRs, and a merged one is drawn only when something here still depends on it.
  • The whole trail is drawn, including the part already walked. A merged prerequisite stays, and so does whatever it declared, so the chain behind an open PR is shown end to end instead of starting halfway along. The arrow leaving a merged card is lighter and labelled ✓ MET: it records a wait that is over, and the PR at its head is not held back by it. A column of nothing but merged cards is headed ALREADY MERGED. A merged PR that nothing here depends on is not drawn at all — this page is about what merges next.

Declaring a prerequisite (the syntax this page reads)

Explicit stacks — a PR whose base branch is another open PR's head — are computed from the GitHub API and are always correct while the prerequisite is open; declaring one anyway is what keeps it drawn after that (see below). The other two kinds GitHub cannot see at all. Either way you write it in the PR body of the PR that is blocked, and it becomes an arrow into its card here:

Depends on #504
Depends on snapshot-labs/snapshot.js#1225
Depends on release of snapshot-labs/snapshot.js#1225
Depends on #504 — reason, shown when you hover the arrow

Stacked on #2219
Stacked on top of #2188 (feat/safesnap-execution)
On top of #2188
  • Depends on #504 — same repo. Satisfied once #504 is merged.
  • Depends on owner/repo#123 — cross-repo. Satisfied once it is merged.
  • Depends on release of owner/repo#123 — cross-repo and release-gated. Merging is not enough: satisfied only once a non-draft release of that repo is published after the PR merged. That edge is marked GATED.
  • Stacked on, Stacked on top of and On top of declare the same thing as Depends on, in the words people actually write on a stacked PR. Each takes the same three forms above.
  • A trailing —, - or : adds a reason to a Depends on line. On the three stack spellings that tail is not read as a reason — what follows one is, in practice, an instruction to the reader (retarget to master after it merges) rather than a description of the dependency, and it is stale by the time the arrow is drawn. Those arrows are labelled with the branch name instead, when you put one in parentheses after the number.

Declare the stack even though this page can compute one. An explicit stack is computed by matching a PR's base branch against the head branches of the repo's open PRs, so it exists only while the prerequisite is open: GitHub retargets the child onto the default branch seconds after the parent merges, and that signal is then gone for good. A merged prerequisite is kept on this page when something declares it, so the line in the body is what carries a stack across the moment it lands — without it the top of the chain disappears exactly when it merges.

Whose PRs appear here. Take the dependency graph and split it into connected chains — everything joined by dependency edges, following them in either direction. A chain is drawn in full if at least one PR in it is tony8713's or @chai3-bot's; a chain with none of theirs in it is not drawn at all. So somebody else's PR is a full card here, with its own prerequisites, and can be the leftmost thing in the picture — what it never is, is unmarked: every card that is not tony8713's is dashed and carries ◇ @handle, and it is not counted in the open-PR total at the top.

Tracked bots. @chai3-bot is tracked here, which means its open PRs seed this page the way tony8713's do: each one anchors its own chain, so it is drawn whether or not anything of tony8713's is joined to it, and it sits wherever its dependencies put it — first column, last, or in the middle, exactly like any other card. There is no rule on this page about where a card may sit; rank comes from edges and nothing else. What tracking does not do is make the work tony8713's: a bot's card is dotted rather than dashed, still carries ◇ @handle, and is counted separately from the open-PR total at the top. A bot's PR in a private repo is withheld and counted in the notice above, on the same terms as tony8713's own.

This replaced a narrower rule — somebody else's PR is drawn only as the target of one of tony8713's edges, never a card of its own — which cut a chain off at the first PR that was not tony8713's and so hid what the rest of it was waiting for. The bound did not change: nothing is on this page that a declared dependency does not join, transitively, to a PR of tony8713's. Being recent, or in the same repo, or interesting, brings a PR no closer to being drawn.

Merged PRs, and the whole trail. One rule decides them: a merged PR is drawn if and only if something on this graph depends on it. A prerequisite that has landed is kept — because the question this page answers, why is that PR still open, is answered by the shape of the whole chain, and a chain that erases itself as it lands answers nothing. It is transitive: if a merged PR drawn here declared a prerequisite of its own, that one is on the same trail and is drawn too, so a merge partway along does not truncate the picture. The other half of the rule keeps the page usable — every PR this build fetches is open, so a merged PR that nothing here depends on is never picked up, and the org's whole merge history does not bury the twenty open PRs this page exists to order.

The trail is merged at both ends of every link. A merged PR's declaration is followed only to a target that also merged: a declaration in a PR that has since merged is a claim about the past, and if its target is still open then the claim was never honoured — the PR merged anyway, so that gate was not real. Drawing the link would put an open card to the left of a merged one and assert it has to merge first, which is not just untrue but unsatisfiable. Those stale links are dropped, and the build log names each one rather than hiding it.

A merged card sits under the chain rule like any other: it is drawn as part of the component that needs it, and dropped with that component if none of tony8713's PRs is anywhere in it. It is never counted in the open-PR total at the top, because it is not open — and if it is somebody else's it keeps its dashed outline and its ◇ @handle marker on top of the merged fill, because whose and what state are two separate channels and neither is allowed to cancel the other.

A merged prerequisite is resolved by number, not out of the open-PR listing that explicit stacks and the candidate sweep are computed from — that listing cannot see a merged PR at all — so it keeps its real title, author and state instead of degrading to a bare number.

Parsing rules, so prose never becomes an edge: the line must start with one of the four keywords (a leading - bullet is fine) and must be nothing but the declaration, so Together with #2219, this will… declares nothing; lines inside fenced code blocks are ignored; and blockquoted lines are ignored, so quoting another PR body — or a GitHub [!IMPORTANT] callout — never declares anything. Nothing on this page is inferred heuristically: an edge exists because somebody wrote it, and which spelling they wrote is the only thing that decides how the line is read.

How this page is built

Merge order runs left to right: an arrow's tail merges before its head, and PRs sharing a column have no order between them at all. Prerequisites GitHub cannot compute come from PR bodies — if an edge is missing here, declare it there. Rebuilt by hand when somebody publishes it, not on a schedule.

The diagram is generated at build time as inline SVG and written into this file as markup. The page loads nothing: no Mermaid, no graph library, no CDN, no font, not one <script> tag. The blocks on this page are native <details> elements, so collapsing the prose off the page cost it no runtime either — the browser opens and shuts them on its own.

The card geometry, the base ink and the arrowheads are presentation attributes on the SVG rather than CSS rules, so the drawing still reads with the stylesheet stripped. What the stylesheet adds is the theming: dark mode, the state fills, and the dash patterns.
